### 3. OCR噪声和质量指标口径

OCR共6216条证据，其中4486条含中文、1953条为单字符。高频内容包括 `1`（110次）、`A`（99次）、`2`（97次）、`-`（87次）、`S`（84次）等；样例也可见碎片化姓名、整屏杂字。

当前GPU OCR服务拼接所有 `rec_text`，未使用识别置信分数筛选，也未把识别框坐标作为细粒度证据保留。质量检查主要把OCR文本与剧本的 `screen_text` 比较，混入对白字幕后容易产生大量“疑似画面文字缺失”，并触发额外复核。

OCR覆盖中位0%、最高12%，不能解释为画面丢失88%—100%。应先区分对白字幕、姓名条、重要画面文字和噪声，再评估遗漏。真实单字对白仍要保留，不能统一删除单字。

### 无效复核、模型重试和长尾

- 模型内部出现36次 `response_create_retry`，常见原因是返回正文不完整（12次）、修正指向允许范围之外（单一报错11次，另有多种组合）。
- 85条复核启动日志中，12次最终复核失败；原因包括越界补丁、2次输出达到长度上限、1次429等。
- 最终质量元数据有32集拒绝复核稿、保留原稿：16集因对白覆盖下降，16集因阻塞问题增多。这是在防止复核造成退化，不能为了速度直接关闭保护。
- 出现1次明确429：模型达到推理限额或被暂停，提示检查方舟模型限额 / Safe Experience Mode。这与余额不足不是同一结论。
- 本地模型并发排队累计仅0.27秒、最大0.11秒；额度等待累计229秒、最大44.67秒。因此直接把当前16并发继续调高，不能针对性解决问题，还可能加重429。
- 主视频COS直连没有记录URL回退；4次Files上传出现明显长尾，两处失败修补均应重点检查裁片上传与连接恢复链路。

## 建议优化顺序

| 优先级 | 优化内容 | 预期作用与约束 |
| --- | --- | --- |
| P0 | 修补片段上传与瞬时网络故障恢复 | 对超时、TLS中断实行有上限的分阶段重试；缓存裁片与已上传文件，续用已完成范围。重试耗尽仍保持review并显示具体失败原因，不能跳过内容门禁。 |
| P0 | 提高复核补丁的有效率 | 给出稳定的原文锚点、集内绝对时间和合法修改区间；明确裁片相对时间的换算；无效补丁提供定点错误反馈。部分补丁只有在可独立验证时才接受，并保留全文回归检查，防止越界或覆盖下降。 |
| P1 | OCR保留置信度和位置，分类、去噪、合并重复字幕 | 减少误报和无效复核；区分字幕与重要画面文字。对单字字幕、姓名条等保留例外，不用粗暴过滤换速度。 |
| P1 | 小范围补台词与说话人证据对齐 | 利用已缓存ASR及相邻镜头补缺；跨集角色上下文辅助归属，保留证据不足时的未知标记，避免凭空猜人。 |
| P1 | 分析OCR队列及GPU利用率 | 记录解码、传输、检测、识别、排队分项，再调批量和证据并发。当前语音约2秒，继续堆语音算力不是主要收益点；不能未经测量盲升并发。 |
| P1 | 模型额度与退避策略匹配 | 按真实RPM/TPM限额配置本地限流、429退避与抖动；不直接修改账户额度或关闭账户保护。 |
| P1 | GPU离线时快速切换 | 新批次开始前健康检查；远端失联后共享短期熔断状态，避免每集重复等待远端超时；CPU回退仍保留质量检查。 |
| P2 | 逐调用成本与可追踪日志 | 模型初识别、复核、失败和重试分别保存usage与金额；下载/OCR/模型/修补日志全部带task_id及attempt，避免并发时统一写成source.mp4而无法归属。 |
| P2 | 门禁统计独立于展示截断 | 当前issues只保存前100条，门禁依赖issues列表；应将完整P0摘要和展示列表分离。本批重算未发现因此漏放行，这项属于预防性代码改进。 |

保持现有空稿拦截、覆盖检查、拒绝退化复核、缓存和CPU回退，不以降低采样率或放宽门禁换取耗时数字。当前视频模型为0.5fps，短剧快速镜头更不适合直接降低采样。

## 成本与验证边界

数据库记录总token为8,559,031，而 `api_cost_rmb` 合计为0。实际输入/输出token估价配置均为0，API未返回金额时会算出0；这不能证明免费或未扣余额。失败、丢弃复核及内部重试的费用也未必完整归入最终任务，应按调用保存并与平台账单核对。

建议先以71、85、55、68、62、66及正常对照集做缓存回放、补丁校验和故障模拟，再用少量代表片段测GPU吞吐和真实收费模型。逐项验证长缺段仍被拦截、修补成功后复检通过、正常集内容不回退、缓存可续用、离线回退正常，再决定是否整剧测试。

可以确认存在减少无效重试和上传长尾的空间，但目前不能给出“优化后一定10分钟”等承诺；同时解决26集待复核可能增加有效修补工作量。新的耗时目标应以小样本端到端测量、质量通过率和费用一起确定。

此次检查基于持久化结果、独立ASR证据抽样、结构覆盖检查和日志，并非90集逐帧观看。本轮未实施上述系统优化，也未增加收费识别调用。

复查工具：`ops/inspect_batch_readonly.py`。使用SQLite只读连接和query_only，提供quality、evidence、events、logs、detail、normalize等查询，不触发provider或修改任务。
